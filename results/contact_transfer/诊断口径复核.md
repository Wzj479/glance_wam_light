# 诊断口径复核：指垫接触不能作为夹持判据

结论：复核六条已保存动作的物理回放轨迹后，`both_pad_contact`（双侧指垫接触）**不能**用来判断「是否建立夹持」，`first_both_pad_loss_state`（首次丢失双侧接触）**不能**用来判断「是否脱持」。此前报告已声明该字段只是代理指标，本次复核给出了同批轨迹上的反例。同时新增末端系相对滑移指标，用共同的 100 状态窗口比较，避免轨迹长度不同造成的混淆。

本次只读取既有回放 CSV，未执行仿真、未推理、未训练，未使用保留状态 45–49。

## 一、口径问题：双侧指垫接触无法区分「没抓住」和「单侧抓住」

| 轨迹 | 双侧指垫接触状态数 | 任一指垫接触状态数 | 抬升 mm | 任务成功 |
|---|---:|---:|---:|---|
| 39 / base | 6 | 30 | 110.12 | 是 |
| 39 / clean | 20 | 45 | 63.79 | 是 |
| **39 / aug** | **0** | 16 | **100.03** | 否 |
| 33 / base | 24 | 27 | 74.83 | 是 |
| 33 / C | 22 | 25 | 74.03 | 是 |
| 33 / P | 0 | 5 | 4.29 | 否 |

39 号 aug 的双侧指垫接触状态数为 **0**，碗仍被抬起 **100.03mm**；39 号 base 双侧接触仅 6 个状态，抬升 **110.12mm**。因此「双侧接触为 0」既不等于未抓取，也不等于未搬运。把 `first_both_pad_contact_state=None` 读成「抓取未建立」在这一批数据上不成立。

## 二、口径问题：首次丢失双侧接触是瞬态量

32 号 base 与 clean 的双侧接触各有两个区间，首次空洞出现在状态 47，随后接触恢复并最终成功。

| 轨迹 | 双侧接触区间数 | 首次空洞状态 | 空洞后是否恢复 | 抬升 mm | 结果 |
|---|---:|---:|---|---:|---|
| 32 / base | 2 | 47 | 是 | 93.73 | 是 |
| 32 / clean | 2 | 47 | 是 | 99.26 | 是 |
| 32 / aug | 1 | 78 | 否 | 102.31 | 否 |

单独报告「首次丢失双侧接触的时刻」会把一个瞬态波动当成释放事件。32 号 aug 的对照特征相反：任一指垫接触跨 121 个状态、**13 个接触区间**，即反复张合，与该轨迹此前记录的「松爪不协调」一致。

## 三、新增指标：末端系相对滑移

定义为碗 body 原点相对末端原点的位置在**末端坐标系**下的逐步变化模长。它直接刻画「夹爪没有跟着物体走」的量。

| 轨迹 | 窗口(100)最大滑移 mm | 窗口平均滑移 mm | 全程最大滑移 mm | 全程最大滑移出现状态 |
|---|---:|---:|---:|---:|
| 39 / base | 12.72 | 5.46 | 12.72 | — |
| 39 / clean | 39.21 | 6.90 | 39.21 | — |
| 39 / aug | 36.85 | 6.98 | 36.85 | — |
| 32 / base | 12.13 | 5.04 | 12.13 | — |
| 32 / clean | 12.50 | 5.02 | 12.50 | — |
| 32 / aug | 44.99 | 5.17 | 44.99 | — |
| 33 / base | 32.06 | 4.86 | 32.06 | — |
| 33 / C | 34.52 | 4.98 | 34.52 | — |
| 33 / P | **11.42** | 5.39 | 46.26 | 285 |

两点需要明确，避免过度解读：

1. **滑移最大值不能单独作为失败判据**。39/clean 窗口最大 39.21mm 却成功；32/base 仅 12.13mm 也成功但与 32/aug 的 44.99mm 同为抬升过百毫米，差别在放置而非抓取。
2. **33/P 的 46.26mm 不代表夹持不稳**。其窗口内最大滑移仅 11.42mm，是三者最低；46.26mm 出现在状态 285，即放弃抓取后手臂继续移动、碗留在桌面所致。这是失败的后果，不是原因。

因此滑移在本批数据上只能作为**描述性指标**，不能当阈值。真正把 33/P 与其余五条区分开的仍是三项一致证据：双侧接触状态数为 0、任一指垫接触仅 5 个状态且分散在 2 个区间、最大抬升 4.29mm。

## 四、尚未完成：手指级接触

最小方案第 1 条还包括「另报左右完整手指碰撞体接触」，本次未能完成，原因与研究结论无关：

- 当前实例 cgroup 内存上限 2 GiB，基线常驻约 1119 MiB。
- `ControlEnv` 构建本身需要约 610 MiB（实测 1361 → 1971 MiB），单进程物理重放总需求约 1485 MiB，当前仅余约 928 MiB。
- 对照验证：用 git HEAD 的**未修改脚本**同样在峰值 2021 MiB 被 SIGKILL，因此这是环境内存不足，不是本次改动引入。

`day1/replay_failure_cases.py` 已加入 `left_finger_contact`、`right_finger_contact`、`any_finger_contact`、`finger_contact_without_both_pads` 与 `relative_slip_mm` 五个字段，并对「指垫接触蕴含手指接触」加断言；`day1/analyze_failure_replays.py` 已加入对应指标与 `contact_transfer.png`。这些代码尚未在物理重放上验证过，需要内存充足的机器重跑既有轨迹才能填上。

在缺少这些列的轨迹上，`day1/analyze_contact_transfer.py` 会在 `finger_contact_columns_present=false` 时明确拒绝把指垫丢失解读为释放，而不是静默按旧口径出数。
