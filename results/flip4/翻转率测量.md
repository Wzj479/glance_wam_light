# 翻转率测量：单次运行的成败能不能用来给模型归因

2026-10-20，A100 40GB。协议 `glance_handover/protocol_flip6_color_strong.json`：
state 26/28/33/34/35/42，`color_strong`，seed 42，6 个回合的 `env_seed` 与归档逐位一致
（1440240074 / 54846745 / 474245375 / 1326985084 / 2145447371 / 981241671），初态相同。

四个模型各重复 5 次，每次都是独立的服务器进程与独立的仿真回合。

## 一、结果

每个格子是"5 次重复里的成功次数"，括号内是步数区间，"轨迹"是 5 次重复产生了多少条
**互不相同**的动作轨迹（由每次运行写下的 `*_actions.npy` 哈希得到）。

| 模型 | ep26 | ep28 | ep33 | ep34 | ep35 | ep42 |
|---|---|---|---|---|---|---|
| base | **4/5**（84–300） | 0/5 | 5/5（80–81） | 0/5 | 0/5 | 0/5 |
| C | 5/5（83–84） | 0/5 | **3/5**（79–300） | 0/5 | 0/5 | 0/5 |
| P | 5/5（83–84） | 0/5 | **5/5**（79–110） | 0/5 | 0/5 | 0/5 |
| P33_initC | **4/5**（84–300） | 0/5 | 5/5（80） | 0/5 | 0/5 | 0/5 |

**轨迹列全部是 5/5。** 每一个 (模型, 回合) 的 5 次重复都产生了 5 条互不相同的动作轨迹，
无一例外。

与归档结果的一致率：

| 模型 | ep26 | ep33 | 28/34/35/42 |
|---|---|---|---|
| base | **0.2**（归档失败，实测 4/5 成功） | 1.0 | 1.0 |
| C | 1.0 | **0.6** | 1.0 |
| P | 1.0 | **0.0**（归档失败，实测 5/5 成功） | 1.0 |

## 二、结论

1. **"状态 33 是 P 特有失败"不成立。** P 在该 state 5/5 全部成功，归档里那次 300 步失败是
   五次中唯一的一次；反而 C 在同一 state 上 2/5 失败。真正翻转的是 C。
2. **"状态 26 是基座特有失败"也不成立。** 基座 4/5 成功，失败率 1/5。
3. **只有 28/34/35/42 是稳定的共有失败**：4 个模型全部 0/5，与归档一致率 1.0。
4. **P33_initC 没有带来可辨识的改进**：ep33 5/5 成功（与 P 相同），28/34/35/42 依旧 0/5；
   唯一差别是 ep26 从稳定成功变成了翻转（4/5）。

## 三、非确定性的来源

同一模型、同一初态、同一协议，动作轨迹每次都不同。候选来源与实测：

| 手段 | 结果 |
|---|---|
| `CUBLAS_WORKSPACE_CONFIG=:4096:8` | 步数稳定在 79，但动作 sha256 仍不同 |
| `torch.use_deterministic_algorithms(True, warn_only=True)` | 步数稳定在 79/80，但 P 的一次运行翻转为 300 步失败 |

即：**非确定性不在 cuBLAS**，而在更靠前的算子；且**换一种数值实现就换一种结果**，
这正是"临界状态"的特征。单独一次运行对 state 33 给出 300 步失败，
和给出 79 步成功，是同一件事的两种合法实现。

## 四、由此确立的评测口径

- 任何"模型特有失败"的表述，都必须附上该 state 的**翻转率**（同初态 ≥5 次重复）。
- 翻转率不为 0 的 state，只能用于描述"该 state 不稳定"，不能用于模型间比较。
- 本设置下可做模型比较的 state 是 28/34/35/42（且只能比较"是否失败"）；
  26/33 只能报告成功率分布。
