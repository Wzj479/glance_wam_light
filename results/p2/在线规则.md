# 在线规则：不用归档信息，也能把三个失败 state 全部救回

2026-10-20。P1 用的是 **oracle 窗口**（从该回合归档轨迹里读出释放动作），所以只证明了
"失败可移除"，没证明"有可部署的修复"。本轮把这层换成**在线规则**，不读任何归档数据。

## 一、规则

> **累计闭合门**：一旦夹爪第一次闭合，任何张爪命令都被抑制，直到本回合**累计闭合步数达到 30**
> 才放行。

- 只数"已经闭合了多少步"，用不到碗高、盘子位置、接触或任何归档信息。
- 阈值 30 来自**成功分布**（每个成功回合闭合约 39–45 步），不是从失败回合的释放时刻调出来的，
  所以"失败能否被修好"是真正的样本外检验。
- 规则只在"第一次闭合之后"生效，接近阶段（尚未闭合）完全不动。

实现：`diagnose_gripper_feedback.py` 新增 `GraspHold`（含 7 个单元测试），
`--driver-args --min-closed-steps 30`。

## 三、结论

1. **三个稳定失败 state 全部救回，15/15（100%）**，且**没有读归档轨迹**。
   这比 P1 的 oracle 窗口还略好（P1 里 28 是 4/5）；差别在噪声范围内，但至少说明在线规则
   没有因为丢了 oracle 信息而变差。
2. **零副作用**：全部基线成功的格子——26、31、33（15 次）、25、29、30（6 次）、
   36 的 C 与 P（6 次）——**27/27 仍然成功**。
   其中 26/base 的归档闭合只有 16 步、36/C 只有 19 步、36/P 只有 18 步，规则**确实会触发**，
   但触发后仍然成功，没有把它们弄坏。
3. **35 仍然 0/5**，与 P1 一致：它的失败在放置阶段（见
   [state35_放置子机理](../p1/state35_放置子机理.md)），不是释放时机，抓取门修不好它。
4. 由此，"提前松爪"这条机理现在有了**可部署的验证**：对这个任务、这四个稳定失败 state，
   一条只看夹爪计数的规则就能稳定修好三个，且不破坏任何成功回合。

## 四、失败过的规则变体（一并记下）

最初还试了"累计闭合 ≥30 **或** 末端抬升 ≥20 mm 就放行"。它在 state 28 上**失败**：
第 60 步末端升了 22 mm，规则放行，但当时只闭合了 23 步，碗随后从 36 mm 掉回 18 mm。
**"抬升过"不等于"夹稳了"**——瞬时抬升会被误判为已完成搬运。去掉这个逃生口、只保留计数门，
才稳定成功。这个反面例子也说明：机理是"释放太早"，不是"没抬起来"。

## 五、口径

- 规则是**任务特定**的：阈值 30 来自"把碗放到盘子"这个任务的成功闭合分布，换任务需重推。
- 这是闭环（有策略推理），干预只改 `action[6]`，六个机械臂通道不动；`--min-closed-steps`
  路径**不使用** `--reference-actions`。
- 35 的 0/5 与"放置失败"一致，但放置阶段本身是否可修（例如换成放到盘心后压一下）
  尚未测试，属另一条线。
